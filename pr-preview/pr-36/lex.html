3 Lexers🔗

 (require parser-combinator/lex) package: parser-combinator

A lexer is a first stage of parsing. It splits text into tokens, such as numbers, names, and punctuation, and drops what the grammar never needs to see, such as whitespace and comments. A grammar written with tok then parses the tokens, so it never mentions what the lexer drops. The rules of a lexer are themselves Parsers over characters, written with the same combinators as any other grammar.

The stages are interleaved: a token is found when the grammar asks for it, so no list of tokens is made. What a lexer makes from a string is an Input, which parse takes as it takes a string.

Lexer : lexer?

A Lexer is made by lexer. It’s a function: applied to a string, it makes an Input of it, whose tokens a grammar over tokens matches.

procedure

(lexer? v) → boolean?

  v : any/c
returns #t if v is a Lexer, made by lexer.

syntax

(lexer [kind rule] ...)

(lexer #:skip skip [kind rule] ...)
 
  skip : (or/c string? Parser)
  kind : symbol?
  rule : Parser
produces a Lexer. Each token comes after whatever skip matches. A string skip is the same as (skip string), which matches any run of its characters. Without skip, nothing is skipped. A token is matched by the first rule that matches some text, and has that rule’s kind, a symbol written as it is for tok, and the rule’s Value as its value. A rule that matches no text is passed over, since a token must have some; only skip can match none.

Examples:
> (define sums
    (lexer #:skip " "
           ['num (pmap string->number (rx #px"\\d+"))]
           ['plus (lit "+")]))
> (define SUM (sep-by+ (tok 'num) (tok 'plus)))
> (parse SUM (sums "1 + 2 +3"))

'(1 2 3)

> (parse SUM (sums "1 + + 2"))

parse: unexpected plus at line 1, column 5

  expected: num

As in alt, the rules are tried in order, and the first to match wins, not the longest. So a rule for a keyword goes before the rule for names, and it still splits a name that begins with the keyword. Lexing keywords as names, and matching them with tok’s value, avoids that.

procedure

(tok kind) → Parser

  kind : symbol?
(tok kind value) → Parser
  kind : symbol?
  value : any/c
produces a Parser that matches one token of the kind kind, producing its value. Given a value too, it only matches a token whose value is equal? to it, such as one keyword among the names. It needs an Input that a lexer made, and given a string, it raises exn:fail.

alt picks its alternatives by the kind of the next token, as it picks them by the next character, so when each alternative begins with its own kind of token, only one of them runs.

Examples:
> (parse (seq (tok 'num 1) (tok 'plus) (tok 'num))
         (sums "1+2"))

'(1 "+" 2)

> (parse (tok 'num) "1")

tok: the input has no lexer; a grammar over tokens parses

what a lexer makes from a string

A parser over characters, such as lit, also works in a grammar over tokens, from the same position. It matches exactly what’s there, so unlike a token, it doesn’t skip what the lexer would before it.

Examples:
> (parse (seq (tok 'num) (lit "!")) (sums "5!"))

'(5 "!")

> ((seq (tok 'num) (lit "!")) (sums "5 !"))

'error

procedure

(with-lexer lex p) → Parser

  lex : lexer?
  p : Parser
produces a Parser that matches what p does, over the tokens that lex finds from where it’s run. It lets a grammar over characters use one over tokens for part of its text, or a grammar over tokens use another lexer’s. What lex skips belongs to the token after it, so p takes what’s skipped before its tokens, and leaves what follows its match to the grammar around it. Where the parse gets furthest inside p, parse’s error says it in lex’s tokens. Given an Input that lex made, p simply runs over its tokens.

Examples:
> (parse (seq (lit "sum=") (with-lexer sums SUM) (lit ";"))
         "sum=1 + 2;")

'("sum=" (1 2) ";")

> (parse (seq (lit "sum=") (with-lexer sums SUM))
         "sum=1 2")

parse: unexpected num at line 1, column 7

  expected: plus or end of input

procedure

(tokens lex str) → (listof token?)

  lex : lexer?
  str : string?
produces the tokens that lex finds in str, to show what a grammar over them sees. Where no rule matches, it raises exn:fail, saying what’s there as parse would, including what it was lexing.

Examples:
> (tokens sums "1 + 2")

(list

 (token 'num 1 0 1)

 (token 'plus "+" 2 3)

 (token 'num 2 4 5))

> (tokens sums "1 + 2x")

tokens: unexpected text "x" at line 1, column 6

struct

(struct token (kind value start end)
    #:transparent)
  kind : symbol?
  value : any/c
  start : exact-nonnegative-integer?
  end : exact-nonnegative-integer?
represents a token: its kind, its value, and the positions in the text where it begins and ends. Parsing doesn’t make tokens; only tokens does.
